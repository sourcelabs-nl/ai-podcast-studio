## Context

See `proposal.md` for motivation. This section only fixes the code paths a focus episode must plug into or diverge from.

**Article consumption.** `EpisodeService.markArticlesAsProcessed()` (`src/main/kotlin/com/aisummarypodcast/podcast/EpisodeService.kt:228-233`) sets `Article.isProcessed = true` for every article in `PipelineResult.processedArticleIds`, called right after `saveEpisodeArticleLinks()` from `createEpisodeFromPipelineResult()` (`EpisodeService.kt:195`). `ArticleRepository.findRelevantUnprocessedBySourceIds` (`src/main/kotlin/com/aisummarypodcast/store/ArticleRepository.kt:12-13`) and `findUnprocessedSince` (`ArticleRepository.kt:18-19`) both filter on `is_processed = 0`, so a processed article never resurfaces as a candidate.

**Schedule advancement.** `createEpisodeFromPipelineResult()` updates `podcast.lastGeneratedAt` (`EpisodeService.kt:195-201`), and `EpisodeWindowResolver.resolve()` (`src/main/kotlin/com/aisummarypodcast/podcast/EpisodeWindowResolver.kt:106-131`) reads the *last episode that actually covered a window* via `findLatestCoveredWindowEnd` to heal gaps. Regeneration already opts out of both (`episode-review`/`async-manual-generation` "Regeneration does not advance the schedule"); a focus episode needs the same opt-out, applied at creation rather than regeneration.

**Article scoring is not per-episode.** `ArticleScoreSummarizer.scoreSummarize()` (`src/main/kotlin/com/aisummarypodcast/llm/ArticleScoreSummarizer.kt:58-150`) scores every newly-seen article exactly once, against `podcast.topic` (`buildPrompt`, `ArticleScoreSummarizer.kt:240`), and persists the result onto the shared `articles` row (`articleRepository.save(updated)`, `ArticleScoreSummarizer.kt:130`). This happens both eagerly (`LlmPipeline.scoreReadySources`, `LlmPipeline.kt:225`) and during generation (`LlmPipeline.aggregateScoreAndFilter`, `LlmPipeline.kt:136-208`), independent of which episode (if any) eventually uses the article. `ArticleEligibilityService.findEligibleArticles()` (`src/main/kotlin/com/aisummarypodcast/llm/ArticleEligibilityService.kt:34-52`) then narrows to the window using `findRelevantUnprocessedBySourceIds(sourceIds, threshold)`, i.e. it **starts from articles already relevant to the podcast's own topic**. A focus can be about anything, so this persisted, topic-scoped score cannot be reused or overwritten for focus purposes.

**Continuity today.** `ChatClientFactory.buildComposeTools()` (`src/main/kotlin/com/aisummarypodcast/llm/ChatClientFactory.kt:71-88`) always registers `HistoryLookupTool` (`searchPastEpisodes`), backed by the `episode_history_fts` table, which is kept in sync by triggers that fire only on `episodes.status = 'GENERATED'` (`src/main/resources/db/migration/V54__add_episode_history_fts.sql`). `webSearch` (`ResearchTool`, `src/main/kotlin/com/aisummarypodcast/research/ResearchTool.kt`) is only registered when `podcast.deepDiveEnabled` (`ChatClientFactory.kt:81-89`), at a 3-call budget (`RESEARCH_TOOL_CAP`, `ResearchTool.kt:21`) versus `HISTORY_LOOKUP_TOOL_CAP = 5` (`HistoryLookupTool.kt:21`). The compose prompt already instructs the LLM to call `searchPastEpisodes` before treating a topic as new, and to skip, follow up, or angle as an update (`episode-history-lookback` spec, `Compose prompt instructs the model to check history`) - this is the existing "mild" mechanism the design reuses rather than inventing a new one.

**Review/approve.** `EpisodeController.approve()` (`src/main/kotlin/com/aisummarypodcast/podcast/EpisodeController.kt:110-127`) accepts `PENDING_REVIEW` or `FAILED` and calls `episodeService.approveAndGenerateAudio()`, which is unaffected by this change. `PodcastController.regenerate()` (`src/main/kotlin/com/aisummarypodcast/podcast/PodcastController.kt:238-253`) and `PodcastService.regenerateEpisodeAsync()` (`src/main/kotlin/com/aisummarypodcast/podcast/PodcastService.kt:445-475`) recompose from a source episode's already-linked articles, but create a **new** `GENERATING` episode row rather than mutating the one under review - not the shape the focus feedback loop needs (repeated recompose of the *same* `PENDING_REVIEW` episode).

## Goals / Non-Goals

**Goals:** score a focus episode's candidates against free text instead of the podcast topic without disturbing the persisted, topic-scoped article scores; keep a focus episode's articles unprocessed and its schedule untouched; give the compose stage of a focus episode always-on, higher-budget research with sources recorded for review; let review recompose the same episode's script repeatedly against the same locked article set.

**Non-Goals:** changing how regular episodes are scored, scheduled, or composed when no focus is involved; a UI for browsing past focus episodes beyond what the existing episode list already shows; changing the TTS/publish flow once a focus episode is approved.

## Decisions

**Focus-scoped candidate selection bypasses the persisted relevance gate.** `ArticleEligibilityService` gains `findEligibleArticlesForFocus(sourceIds, podcast, window)`, built on `ArticleRepository.findUnprocessedSince(sourceIds, since)` (`ArticleRepository.kt:18-19`, no relevance filter) instead of `findRelevantUnprocessedBySourceIds`, then applying the same window and evergreen filters `findEligibleArticles` already applies. This is necessary because a focus can be about something the podcast's general topic would score low (or an article the podcast's topic would score low can be exactly on-focus); starting from the topic-filtered set would silently exclude focus-relevant articles that never cleared the general threshold.

**Focus relevance is scored fresh, not persisted onto `articles`.** `ArticleScoreSummarizer` gains a non-persisting entry point, e.g. `scoreForFocus(articles, focus, podcast, filterModelDef)`, reusing `buildPrompt`'s structure with the focus text substituted for `podcast.topic` (a `topicOfInterest: String` parameter takes the place of reading `podcast.topic` directly), but returning `Map<Long, ScoreSummarizeResult>` instead of calling `articleRepository.save()`. This keeps the podcast-wide `relevance_score`/`summary`/`subtopic` columns meaning what every other read of them assumes: relevance to the podcast's own topic. An article's focus-episode summary, if different from its stored one, is only used within that focus episode's compose input, not persisted back onto `articles`.
- Alternative rejected: temporarily overwrite `podcast.topic` with the focus text and call the existing persisting `scoreSummarize()`. Rejected because scoring runs concurrently with eager background scoring (`scoreReadySources`) for the same podcast, and persisting a focus-scoped score onto the shared row would corrupt the general-topic score the very next regular episode relies on.

**No relevant articles is a hard failure.** The focus pipeline stage filters `scoreForFocus` results by `podcast.relevanceThreshold` (same threshold as regular episodes; focus does not introduce a second threshold) and raises an exception with a message naming the focus text when the filtered set is empty, caught by the existing `failEpisode` path (`PodcastService` catch blocks around `runGenerationPipeline`/`runRegeneration`) so the episode lands in `FAILED` with that message in `errorMessage`, exactly like any other pipeline failure.

**Consumption and schedule are skipped wherever an episode's lifecycle touches them, keyed on `Episode.focus != null`.** Manual generation does not go through `createEpisodeFromPipelineResult()`: it creates a `GENERATING` row via `EpisodeService.createGeneratingEpisode()` (which bumps `lastGeneratedAt` up front) and completes it in `finalizeEpisode()` (which marks the linked articles processed and bumps `lastGeneratedAt` again), and `failEpisode()` bumps it on failure. Each of these reads the episode's `focus` and, for a focus episode, skips the `lastGeneratedAt` update and the marking of articles as processed, and `finalizeEpisode()`/`createEpisodeFromPipelineResult()` force `PENDING_REVIEW` regardless of `podcast.requireReview`. Article links are still written, so traceability and review display are unaffected.

**A focus episode is invisible to the regular schedule's queries.** `EpisodeRepository.findLatestCoveredWindowEnd` (window healing) and `findRecentGeneratedByPodcastId` (the dedup stage's history) both filter `focus IS NULL`: a focus episode's window must not move the next regular window's start, and its unconsumed articles must not be treated as already covered by the dedup gate, which would be a hard exclusion rather than the mild continuity nudge below. `EpisodeService.hasActiveEpisode(podcastId, focusEpisodes)` counts regular and focus episodes apart, so a focus episode waiting for review does not hold up the scheduled regular episode, and at most one episode of each kind is active at a time.

**The focus path has no dedup stage.** `LlmPipeline.selectForFocus()` aggregates unlinked posts, selects via `findEligibleArticlesForFocus`, gates on a scoring-only cost estimate against `maxLlmCostCents`, scores via `scoreForFocus`, keeps articles clearing `relevanceThreshold` and applies the usual compose cap. The focus is the selection, so clustering and the already-covered gate do not apply. The selection's links and score-stage cost are persisted by `EpisodeService.saveFocusSelection()`; no candidate rows are written, since `episode_candidate_articles` costs its dropped candidates from the persisted topic-scoring tokens.

**Research is forced on and budget-raised via the existing tool-registration path, not a second tool.** `ChatClientFactory.buildComposeTools()` takes the episode (or its `focus`) so it can register `ResearchTool` when `podcast.deepDiveEnabled || context.focusResearchEnabled`, and register its budget via `researchCapFor(context)` (`FOCUS_RESEARCH_TOOL_CAP` for a focus episode, else `RESEARCH_TOOL_CAP`); `ChatClientFactory.createForCompose()` takes the `ComposeContext` for this (`FOCUS_RESEARCH_TOOL_CAP = 5`, alongside the existing `RESEARCH_TOOL_CAP = 3` in `research/ResearchTool.kt`). `ComposeContext` gains `focus: String?`, with `focusResearchEnabled` derived as `focus != null`, so `buildWebSearchBlock(deepDiveEnabled, ...)` call sites in `BriefingComposer`/`DialogueComposer`/`InterviewComposer` (each around their `Engagement techniques:` line) call `buildWebSearchBlock(podcast, context, hasSubtopics)`, which enables the block for `podcast.deepDiveEnabled || context.focusResearchEnabled`, states the actual budget, and uses focus-specific wording for a focus episode, so the prompt text mentions `webSearch` whenever the tool is actually registered. A shared `buildRunContextBlock(context)` appends the focus text, the recent focus episodes and the reviewer feedback to all three compose prompts.

**Research sources are recorded as a new table, mirroring `episode_candidate_articles`.** `V79` adds `episode_research_sources(id INTEGER PRIMARY KEY, episode_id INTEGER NOT NULL, query TEXT NOT NULL, title TEXT NOT NULL, url TEXT NOT NULL, ordinal INTEGER NOT NULL)` (an `episode_candidate_articles`-shaped table, `src/main/kotlin/com/aisummarypodcast/store/EpisodeCandidateArticle.kt`, is the closest existing precedent for "per-episode record of an LLM tool's output"). `ResearchTool.webSearch()` (`research/ResearchTool.kt:44-60`) gains an optional episode id (present only when composing a focus episode) and, after a successful Tavily call, persists one row per hit through a small `EpisodeResearchSourceRepository`. Recording happens in the tool rather than in the composer, because the tool is the only place that sees both the query and the raw hits together.

**Migration `V79` also adds `episodes.focus TEXT NULL` and `episodes.review_feedback TEXT NULL`.** `Episode` (`src/main/kotlin/com/aisummarypodcast/store/Episode.kt:16`) gets matching nullable fields; the API response mapper (`PodcastMappers.kt`) exposes `focus` and `reviewFeedback` on `EpisodeResponse`. Recorded research sources are served by `GET /users/{userId}/podcasts/{podcastId}/episodes/{episodeId}/research-sources`.

**Feedback recompose reuses the regeneration pipeline shape but mutates the same row.** Rather than `PodcastService.regenerateEpisodeAsync()` (which creates a new `GENERATING` episode), `PodcastService.recomposeFocusEpisodeAsync(episode, podcast, feedback)` (behind `POST .../episodes/{episodeId}/regenerate-script`, 409 via `EpisodeNotRecomposableException` unless the episode is a focus episode in `PENDING_REVIEW`) runs in the background against `EpisodeService.findLinkedArticlesAndTopics(episode.id)`, the same locked set. The focus summaries are never persisted, so it first reruns `LlmPipeline.scoreForFocus()` on that locked set (the LLM cache replays the first run's calls), clears the episode's recorded research sources, composes with `ComposeContext(focus, extraInstruction = feedback)` so research reruns and records afresh, and stores the result through `EpisodeService.saveFeedbackRecompose()`, which writes the script and compose cost onto the existing row, sets `review_feedback`, and leaves the status at `PENDING_REVIEW`. The recap is regenerated so the history index reflects the final script. While it runs, `pipelineStage` is set so the review screen shows progress; a failed recompose clears it and leaves the previous script under review rather than failing the episode.
- Alternative rejected: reuse `regenerateEpisodeAsync` and discard the previous `PENDING_REVIEW` row on each feedback submission. Rejected because it multiplies episode rows for what the reviewer experiences as one episode being iterated on, and it would need extra logic to keep `episode_research_sources`/`episode_articles` attached to whichever row is "current".

**Focus-episode continuity is a data flag plus a prompt nuance, not a new lookup path.** Once a focus episode's status reaches `GENERATED` (after approval and TTS), the existing `episode_history_fts` triggers index it exactly like any other episode (`V54__add_episode_history_fts.sql`), so `searchPastEpisodes` already surfaces it to the next regular episode's compose stage without any new indexing work. `HistoryLookupTool.searchPastEpisodes()` (`HistoryLookupTool.kt:44-68`) and `EpisodeHistoryRepository.search()` (`EpisodeHistoryRepository.kt:18-42`) are extended to also select `episodes.focus IS NOT NULL AS is_focus_episode` and return it as `PastEpisodeMatchDto.isFocusEpisode`. The compose prompt's existing "check history before treating a topic as new" instruction (`ComposerUtils`/composer prompt text, "Engagement techniques" block) gains one clause: when a match has `isFocusEpisode = true`, treat it as a continuation to build on with new developments rather than a topic to skip, and reuse of the same articles is allowed rather than avoided. To make sure the continuation does not depend on the model thinking to search, the compose prompt of a regular episode also names every focus episode generated since the previous regular episode (its focus text and date), with the instruction to look it up via `searchPastEpisodes` and treat that topic as a follow-up. This directly satisfies the "mild, not hard-exclusion" requirement using the mechanism the compose stage already calls into, rather than adding a second continuity channel that could disagree with the first.

**Frontend.** The Focus field on `frontend/src/app/podcasts/[podcastId]/upcoming/page.tsx` (`handleGenerate`, lines 291-308) sends `{ focus }` in the `POST /generate` body only when non-empty, matching how the page already conditionally builds request bodies elsewhere on this page. The review screen (episode detail page) reuses the page's existing word-count-to-minutes calculation (`WORDS_PER_MINUTE`, already computed for the preview at `upcoming/page.tsx:336-341`) for the focus episode's estimated length, and adds a research-sources list and a feedback textarea + "Regenerate script" button that calls the new recompose endpoint, all in a `FocusReviewPanel` (`frontend/src/components/focus-review-panel.tsx`) shown on the episode detail page for a focus episode; the selected articles are the page's existing Articles tab and the estimated length its existing header figure. "Generate Episode" on the upcoming page opens a confirmation `AlertDialog` first (the page's existing pattern for full-audio generation), stating regular or focus (with the focus text) and the number of upcoming articles considered; nothing is POSTed until it is confirmed.

## Risks / Trade-offs

- [A second, ephemeral scoring pass costs extra LLM calls beyond what eager background scoring already spent] → Bounded by the same per-podcast cost gate pattern (`CostEstimator`/`maxLlmCostCents`) already applied to `aggregateScoreAndFilter`; the focus pipeline estimates and gates its own scoring pass the same way before making calls.
- [Widening candidate selection to `findUnprocessedSince` (no relevance floor) could pull in a very large, unscored-by-topic backlog for an old/quiet podcast] → The existing window filter and `maxArticleAgeDays`/`maxWindowDays` caps already bound this the same way they bound a regular episode's candidate pool.
- [A focus episode's `webSearch` results recorded per-episode grow `episode_research_sources` unbounded over time] → Same shape as `episode_candidate_articles`, which already accumulates per-episode without cleanup; no new retention policy is introduced by this change.
- [Repeated feedback recompose on the same episode row loses the script from the previous attempt] → Acceptable: `review_feedback` only needs to hold the latest feedback per the requirement, and the script itself remains editable/visible at every stage exactly as any `PENDING_REVIEW` episode's script already is.

## Migration Plan

`V79__add_focus_episode_fields.sql` adds the four new columns/table (`episodes.focus`, `episodes.review_feedback`, `episode_research_sources`) additively; no backfill needed since existing episodes simply have `focus = NULL`. No rollback tooling beyond the project's existing Flyway conventions (`.claude/rules/pom.md` scope does not apply here; see `flyway-migration` skill for versioning conventions). Deploy is a single release: schema + backend + frontend land together, since the frontend's Focus field depends on the backend accepting it and the review screen depends on the new columns/table existing.
